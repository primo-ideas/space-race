# CLAUDE.md

Project context and working rules for Claude Code. The game is called Space Race, renamed on 2026-09-23 along with a repository of its own, whose history starts there: `origin` is `https://github.com/primo-ideas/space-race.git`, and the README badges point there.

## Working rules

- **Language:** everything in the repository (code comments, docs, README, CLI help, logs, commit messages) is in English, except translation files. Talk to the user in French.
- **Commits and versions:** every commit is a version, titled `vX.Y.Z: <summary>` with a description of what changed and why. The user makes the minor and major versions. Claude commits patch versions on its own whenever it judges a coherent set of changes done and verified (builds, tests pass), and bumps the crate versions to match. Claude does not push unless asked.
- **Crate names:** kebab-case (`space-race-*`), following Cargo conventions.
- **Machine:** since 2026-09-23, a Windows 11 machine: i5-9600K (6 cores), GTX 1050 Ti, 16 GB. A debug build of the workspace from nothing takes 26 minutes, an incremental one seconds, and the client runs at 130 to 330 fps. No Python on it: scratch scripts go in PowerShell, bash or Rust. The Cargo build lock can be held by rust-analyzer or by a build the user started: if it is, ask rather than block on it.
- **Builds:** build and run in debug, the user's decision on getting this machine (`cargo build --workspace --all-targets`, then `target/debug/space-race-server` and `target/debug/space-race-client`, or `run.ps1`). The dev profile optimizes every dependency, so Bevy runs at full speed and only our own code is lightly optimized (docs/architecture.md). Always build with `--workspace`: building a single crate with `-p` changes the unified features and recompiles Bevy, which took over 20 minutes once. The one exception is the web build, still in release, `cargo build --release -p space-race-client --target wasm32-unknown-unknown` (the server cannot compile to wasm; the wasm target has its own cache). See docs/web.md.
- **Docs:** `docs/` holds the reasoned technical decisions. Update it in the same change as the code it describes, and link new pages from `docs/README.md`. This file keeps the working rules and the current status; it must not duplicate `docs/`.
- **Self-verification:** build non-interactive test modes early so Claude can check its own work (client `--capture <file.png>` screenshot mode, later scripted inputs with assertions, server logs, client/server integration tests). The user judges game feel and online latency.

## Project

Online multiplayer racing game, "best and modern" Rust stack. License: the Unlicense; the README states that Claude writes all the code. No art direction yet: simple geometric assets, which may become the game's identity.

Cargo workspace:
- `client/`: Bevy 0.19, native and web (wasm, WebGL2; built with `wasm-bindgen` 0.2.128 and `client/web/index.html`, settings from the page address). Screens: login (nickname, generated or remembered), lobby browser with a creation dialog; menu choices remembered between runs (docs/ui.md), except a generated nickname the player never edited, lobby (race view, HUD, results, spectating); mouse, keyboard and gamepad everywhere (docs/ui.md). Predicts the player's own car on a timeline ahead of the server and reconciles it with the snapshots, interpolates the other cars (displayed 50 ms in the past) (docs/latency.md), chase camera, which cuts between fixed shots once the player has finished the race. Sound synthesized in code, no audio file (docs/sound.md), volume from `--volume`. Touch interface for phones in a browser: on-screen controls over the race and compact menus (`ui/touch.rs`, docs/ui.md). Unattended checks: `--nickname`, `--lobby`, `--track`, `--laps`, `--min-players`, `--create-dialog`, `--autopilot`, `--autopilot-drift`, `--touch`, `--latency` (the figures of docs/latency.md over the race; F3 toggles them), native-only `--capture <png> --capture-delay <s>` and `--window-size <WxH>`. `run.ps1` runs server and client on Windows.
- `server/`: no Bevy (the user doesn't want the ECS there). Fully async on tokio, axum WebSocket at `/ws`, listening on `127.0.0.1:8080`. Player-created lobbies: a directory task, one task per lobby ticking at 60 Hz (docs/lobbies.md). Game data in `server/data` (`--data-dir`): every `tracks/<key>.ron` (one today, `esplanade`, the circuit the drift is drawn for) and `car.ron`, hot-reloaded every second. A track file also places its bottlenecks, stretches where the road pinches in, and its scenery: props standing beside the road, written from the road rather than in world coordinates, which the client builds and the simulation never sees (docs/tracks.md).
- `protocol/`: no Bevy. The wire (bitcode, one message per binary WebSocket frame) and, as a module rather than a crate, the auth those messages carry.
- `sim/`: no Bevy. The driving simulation: tracks, car, race progress and ranking, autopilot. Run by the server with full authority, and by the client to predict the player's own car: both step it through the same code (`Car::step`, `race::racing_tick`). It depends on nothing else here and knows nothing of the wire; `protocol` depends on it. Math types must use the same `glam` version as Bevy, pinned once in `[workspace.dependencies]`.
- `logger/`: how the binaries log. It exists so the level is set explicitly in one place: Bevy's feature unification turns on `env-filter`, which silences a plain `fmt::init()`. Only the server calls it, Bevy owning the client's subscriber.

Auth (alpha, no account/mail/password): the client keeps an Ed25519 key (native: `%APPDATA%\Space Race\data\identity.key`). Handshake: `Hello{version, nickname, public_key}` → `Challenge{nonce}` → `ChallengeResponse{signature}` → `Welcome{tracks}` or `Rejected(reason)`. Player identity = public key.

## Gameplay direction

- A long phase in a minimal, deliberately ugly test environment comes before any fun gameplay feature. The goal is **perfect handling** in a simple context: accelerate, steer left and right, and soon drift.
- **No brake, ever**: the game is full speed all the time. Controls: gamepad R (right bumper, not the trigger) accelerates by default, left stick steers; keyboard W accelerates, A / D steer (read by key position; do not mention keyboard layouts).
- **Drift is the heart of the gameplay**, in the spirit of Rocket Racing (Psyonix, in Fortnite): holding drift through a turn builds up a boost released on exit, and fills a turbo meter. First version in v0.1.12 (protocol 6): gamepad X or keyboard Shift, held with the stick turned, locks a side, slides without losing speed, charges, and pays out a boost on release; a wall loses the charge. Refined in v0.1.13 at the user's request: less thrown to the outside (the body angle is only drawn, the path follows the drift radius), no speed lost leaving a drift, a boost that is felt. v0.1.14, user's request "like Rocket Racing, a new driving mode where it skates": the drift answers the stick at once (`drift_steering_response`), the path sticks to the heading, the body swings 20 to 45 degrees. v0.1.16, user's feedback "path better, but steer much more gently in a drift, feel it unscrew and glide": drift rotation and body swing build up over 0.6-0.75 s (`drift_steering_response` 4, `drift_angle_response` 3), path still following the heading. v0.1.18, user's request "the longer you hold a drift, the more it should brake you": the drag grows with the charge (`drift_drag_ramp`), so a drift is taken through a turn and let go of. Both to be judged. Rebuilt on 2026-09-20 at the user's request "on passe en drift quand on desaxe [...] pas oblige de maintenir la touche, mais si on le fait on serre davantage les virages [...] quand on repasse dans l'axe de la velocite, on sort du drift, sauf si on maintient": `Car::slip` is no longer a drawn angle but the real one between the nose and the travel, so the drift starts by turning hard past `drift_entry_angle`, ends by coming back under `drift_exit_angle` unless the button is held, and the stick sets a signed curvature -- centered runs straight, against the drift catches the slide. The button only tightens, and costs speed. A real slide runs wide, which is why `esplanade` is 28 m and why `serpentine` was deleted rather than widened (docs/simulation.md, docs/tracks.md). To be judged: the feel, and `drift_grip` (4.0) above all. The turbo meter (three charges) is still to do.
- **Start boost** (v0.1.13, user's request): pressing accelerate right at the start gives a boost graded S to E, timed on the tick the client displayed.
- First milestone: very clean handling on curved roads. The server has full physical authority, loads the test circuit (a small oval) from a file, the client downloads it, and the user can drive it with a gamepad. "Curved turns" means **banked turns**: done in v0.1.10, the road curving up toward the outer wall (parabolic cross-section, 30° at the outer edge on the hippodrome), rising along the clothoid transitions with a smoothstep, gravity pulling toward the inside.
- Look: black background, the track alone (no ground), dark road, walls striped dark gray and neon blue, neon blue centerline dashes. Menus: dark translucent panels, neon blue accent, Saira font (OFL, the one file not in the public domain), animated neon grid behind.
- Lobbies (v0.1.11, user's choices): created by players, gone when empty; settings name, track, laps (default 3), players to start (default 2), max players. Waiting (driving freely) → grid 6 s as soon as there are enough players (user's request: 3 s silent, then 4 start lights one a second, the 4th, green with its own burst, lighting at the very start; v0.1.16) → race of N laps (ends when all finished or 30 s after the first) → 8 s results, during which whoever crossed the line is still watching their car drive itself (v0.1.11, the user's report that a solo race gave the wheel straight back) → again. Joining on the grid races; joining after the start spectates until the next one.

## Deployment constraints (certain)

- The server runs on the user's Scaleway machine behind an Apache reverse proxy. Apache terminates TLS (Let's Encrypt) and forwards in plain text to `127.0.0.1:8080`. This rules out QUIC/WebTransport and TLS client certificates.
- **No self-signed certificates.** If native TLS is ever needed, do it properly with a local fake CA.
- The client ships as native desktop **and** wasm. The web build is deployed to `https://primo-ideas.xyz/space-race/` by `deploy/deploy.ps1` (docs/deploy.md), which also installs the game server there; gamepad play in the browser is expected. Keep every client dependency wasm-compatible.
- Mobile browsers, landscape (v0.1.12, the user's request, their design): the left thumb steers on two buttons, left and right; the right thumb holds a cross -- touching it anywhere accelerates, and sliding from its hub onto a branch calls that branch's function. Drift is the first branch, straight up; the other three are drawn as the empty slots they are, waiting for the turbo and what follows. The whole interface follows: the menus are laid out for a screen 440 units high instead of 720, the browser drops its details panel, the HUD leaves the thumbs their corners and gains a LEAVE button, and no key hints are shown. The client asks the browser whether the pointer is coarse; `?touch` or `--touch` forces it (docs/ui.md, docs/web.md). **Never tried on a real phone.**

## CI

Five separate GitHub workflows (separate README badges): build server, test server (server + protocol + sim + logger), build client native (Linux), build client wasm, and deploy. The deployment could not exist before September 2026: the old machine had no IPv4 (the user would not pay for one), GitHub-hosted runners have no IPv6 egress, and github.com has no AAAA at all, so neither direction was reachable. The new Scaleway machine has an A record as well as an AAAA one, so `deploy.yml` runs the tests and then cross-compiles, uploads and installs, on a push to main or on demand. It needs the `DEPLOY_SSH_KEY` repository secret and a machine set up by the user's `~/Documents/setup-server.sh`, which is outside both repositories because it sets up the whole host. `deploy/deploy.ps1` stays, for putting a build online without a commit (docs/ci.md, docs/deploy.md).

Most turns run into the next with no road between them. Six are banked, the tightest is a 165° hairpin around 28 m two thirds of the way round, and the fast third of the lap is three sweepers of 65 to 99 m radius. **Bottlenecks** are the new thing in the track format: a `narrows` list pinches the road from 28 m down to 13, 14 and 15 m over a stretch, blending in and out along the same smoothstep as the banking. The centerline never moves and both walls come in, so a bottleneck is the same corner with the room taken away; everything reads the width where it stands -- the wall a car is pushed off, the road and walls the client builds, the props beside them, the grid, the camera, the menus' thumbnail -- so an arch over a bottleneck is narrower than one over open road. 83 props dress the lap: an arch over the line and over each bottleneck, boards into every turn, stands around the turns worth watching, pylons at the apexes, slabs out in the dark. The geometry was designed with a scratch tool that integrates the same clothoids as `sim` and draws the circuit to a PNG, so the loop closes to 1 cm, the road never comes within 39 m of itself and no prop stands on another part of the lap. It was written on the old machine without being built, and first built and run on the new one (2026-09-23): the drifting autopilot scraped the gate for nine ticks, its walls closing inside the exit of the esses while the car was still 7 m out, so the gate moved from 694 to 712 m, narrow over the end of the straight and into the fast right as its comment always said; the funnel went from 14 to 15 m, having left the drift 0.1 m, and the squeeze from 15 to 14 (docs/tracks.md, "Placing one"). The autopilot now laps it drifting in 39.2 s against 41.5 s gripping, both clean; six ticks late, only the gripping lap is.
- Deployment (2026-09-20, the user's request after taking a bigger Scaleway machine and pointing the A and the AAAA at it from Gandi): three pieces. **`~/Documents/setup-server.sh` on the user's machine, outside both repositories**, sets the whole host up and is the only file that knows both games exist: the Apache modules, and then per game -- a `GAMES` table at the top, each game's name and loopback port, this one on 8081 and Dronoid on 8080 -- the system user, the home, the web directory, the systemd unit, `/etc/apache2/<name>.conf`, and one `Include` line inside the `SSLEngine on` block of the virtual host, backed up and `configtest`ed with a rollback. `--ci-key` (repeatable), `--only`, `--dry-run`. **It never upgrades the system and never touches TLS**, both being the user's own (they said so from the first message, and said it again when a version of the script had taken them on): the only package it will install is `apache2`, on a machine that has none, and its whole dealing with TLS is reading the virtual host certbot wrote to add a line to it. It never writes to `/var/www/html` itself, only to the games' directories under it, because a landing page is coming there. `deploy/install.sh` still replaces the build and nothing else, refuses a machine that was never set up, and now fails if the service does not come back up. `.github/workflows/deploy.yml` runs the tests, then cross-compiles to `x86_64-unknown-linux-musl`, builds the release wasm client, uploads and installs, and checks the page, the module's media type and that `/space-race/ws` is not a 404; it needs the `DEPLOY_SSH_KEY` secret. `deploy/deploy.ps1` stays for a build without a commit and gained `-UploadOnly`. The user keeps the security deliberately light: a personal machine, an unknown project. **Not verified: none of this has been run against the new machine yet.**
- `shared/` split on 2026-09-20 at the user's request, following how Dronoid keeps its common part: `protocol/` (the wire, with auth as a module, since the handshake messages carry the keys and nonces), `sim/` (the whole of the driving, five sixths of the old crate, depending on nothing else and knowing nothing of the wire) and `logger/` (the log setup, the one place the level is set explicitly; only the server calls it, Bevy owning the client's subscriber). - Input lag (2026-09-22, the user's decision to "work hard on input lag", measuring first): there is no client-side prediction; the player's own car is displayed from snapshots like every other. v0.1.14 measures it (protocol 12): inputs are numbered, every car in a snapshot echoes the last input number its driver had sent, and a ping is answered at once. The client times the ping, each input to the snapshot including it and to the frame displaying it, the buffer and the frame, shows them on F3 and logs them at info every 5 s (docs/latency.md). First figures, local server, Windows, 60 fps: ping 1-2 ms, input to server 12-15 ms, **input to screen 70-89 ms, of which about 60 are the client's own** (interpolation buffer and the once-a-frame check). v0.1.15 predicts the player's own car (protocol 13): a timeline ahead of the server by a round trip and two ticks, each input stamped with the tick it takes effect on and held by the server until then, the tuning sent in the lobby state, the start graded on the tick the press takes effect through the shared `race::racing_tick`, reconciliation from the newest snapshot, corrections gliding out unless over 6 m. Same bench: **input to screen 33-34 ms** (from 70-89), **correction 0.0 cm, worst 0.0**, across whole races and a predicted S start. Waiting on the user's judgement: the feel, above all online. Next ideas in docs/latency.md: a frame less by predicting one tick further. Not measured against the deployed server (the native client cannot reach `wss://`; it is the web client's to measure).
