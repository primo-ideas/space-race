# CLAUDE.md

Project context and working rules for Claude Code. The game is called **Star Racer** since 2026-11-11 (v0.1.26, the user's word: "The project is now called Star Racer"). It was Space Race from 2026-09-23, when it got a repository of its own, whose history starts there; its versions restarted at v0.1.0 with it, so the older versions this file names in Gameplay direction, v0.1.10 to v0.1.24, are from the history before it. The GitHub repository is `primo-ideas/star-racer` (`origin` is `https://github.com/primo-ideas/star-racer`), and the checkout is the folder `star-racer`.

## Working rules

- **Language:** everything in the repository (code comments, docs, README, CLI help, logs, commit messages) is in English, except translation files. Talk to the user in French.
- **Commits and versions:** every commit is a version, titled `vX.Y.Z: <summary>` with a description of what changed and why. The user makes the minor and major versions. Claude commits patch versions on its own whenever it judges a coherent set of changes done and verified (builds, tests pass), and bumps the crate versions to match. Claude does not push unless asked.
- **Crate names:** kebab-case (`star-racer-*`), following Cargo conventions.
- **Machine:** since 2026-09-23, a Windows 11 machine: i5-9600K (6 cores), GTX 1050 Ti, 16 GB. A debug build of the workspace from nothing takes 26 minutes, an incremental one seconds, and the client runs at 130 to 330 fps. No Python on it: scratch scripts go in PowerShell, bash or Rust. The Cargo build lock can be held by rust-analyzer or by a build the user started: if it is, ask rather than block on it.
- **Builds:** build and run in debug, the user's decision on getting this machine (`cargo build --workspace --all-targets`, then `target/debug/star-racer-server` and `target/debug/star-racer-client`, or `run.ps1`). The dev profile optimizes every dependency, so Bevy runs at full speed and only our own code is lightly optimized (docs/architecture.md). Always build with `--workspace`: building a single crate with `-p` changes the unified features and recompiles Bevy, which took over 20 minutes once. The one exception is the web build, in its own size-first `web` profile, `cargo build --profile web -p star-racer-client --target wasm32-unknown-unknown` (the server cannot compile to wasm; the wasm target has its own cache). See docs/web.md.
- **Docs:** `docs/` holds the reasoned technical decisions. Update it in the same change as the code it describes, and link new pages from `docs/README.md`. This file keeps the working rules and the current status; it must not duplicate `docs/`.
- **Self-verification:** build non-interactive test modes early so Claude can check its own work (client `--capture <file.png>` screenshot mode, later scripted inputs with assertions, server logs, client/server integration tests). The user judges game feel and online latency.

## Project

Online multiplayer racing game, "best and modern" Rust stack. License: the Unlicense; the README states that Claude writes all the code. No art direction yet: simple geometric assets, which may become the game's identity.

Cargo workspace:
- `client/`: Bevy 0.19, native and web (wasm, WebGL2; built with `wasm-bindgen` 0.2.129 and `client/web/index.html`, settings from the page address). Screens: the first screen (nickname, generated or remembered, QUICK PLAY and QUEUE FOR RANKED, then the lobby list, the leaderboard, the settings -- rebindable keys and gamepad buttons, vibration, and on a phone the layout of the touch controls -- and natively a QUIT button), lobby browser with a creation dialog; menu choices remembered between runs (docs/ui.md), except a generated nickname the player never edited, lobby (race view, HUD, results, spectating); mouse, keyboard and gamepad everywhere (docs/ui.md). Predicts the player's own car on a timeline ahead of the server and reconciles it with the snapshots, interpolates the other cars (displayed 50 ms in the past) (docs/latency.md), chase camera, which cuts between fixed shots once the player has finished the race. Sound synthesized in code, no audio file (docs/sound.md), volume from `--volume`. Touch interface for phones in a browser: on-screen controls over the race and compact menus (`ui/touch.rs`, docs/ui.md). Unattended checks: `--nickname`, `--lobby`, `--track`, `--laps`, `--min-players`, `--create-dialog`, `--settings`, `--autopilot`, `--autopilot-drift`, `--quick-play`, `--ranked`, `--touch`, `--safe-area`, `--latency` (the figures of docs/latency.md over the race; F3 toggles them), native-only `--capture <png> --capture-delay <s>` and `--window-size <WxH>`. `run.ps1` runs server and client on Windows.
- `server/`: no Bevy (the user doesn't want the ECS there). Fully async on tokio, axum WebSocket at `/ws`, listening on `127.0.0.1:8080`. Player-created lobbies: a directory task, one task per lobby ticking at 60 Hz (docs/lobbies.md); quick play, the ranked queue, matchmaking and the ladder (`--ratings`, default `ratings.ron`; docs/ranked.md). Game data in `server/data` (`--data-dir`): every `tracks/<key>.ron` (one today, `skyway`, a road that turns, climbs, dives and banks all the way round) and `car.ron`, hot-reloaded every second. A track file also places its relief, heights the road passes through; its bottlenecks, stretches where the road pinches in; and its scenery: props standing beside the road, written from the road rather than in world coordinates, which the client builds and the simulation never sees (docs/tracks.md).
- `protocol/`: no Bevy. The wire (bitcode, one message per binary WebSocket frame) and, as a module rather than a crate, the auth those messages carry.
- `sim/`: no Bevy. The driving simulation: tracks, car, race progress and ranking, autopilot. Run by the server with full authority, and by the client to predict the player's own car: both step it through the same code (`Car::step`, `race::racing_tick`). It depends on nothing else here and knows nothing of the wire; `protocol` depends on it. Math types must use the same `glam` version as Bevy, pinned once in `[workspace.dependencies]`.
- `logger/`: how the binaries log. It exists so the level is set explicitly in one place: Bevy's feature unification turns on `env-filter`, which silences a plain `fmt::init()`. Only the server calls it, Bevy owning the client's subscriber.

Auth (alpha, no account/mail/password): the client keeps an Ed25519 key (native: `%APPDATA%\Star Racer\data\identity.key`). Handshake: `Hello{version, nickname, public_key}` → `Challenge{nonce}` → `ChallengeResponse{signature}` → `Welcome{tracks}` or `Rejected(reason)`. Player identity = public key.

## Gameplay direction

- A long phase in a minimal, deliberately ugly test environment comes before any fun gameplay feature. The goal is **perfect handling** in a simple context: accelerate, steer left and right, and soon drift.
- **No brake, ever**: the game is full speed all the time. Controls, by default: gamepad R (right bumper, not the trigger) accelerates, left stick steers, **the right trigger drifts and Y / triangle fires the turbo** (the user's word on 2026-11-11: "Le drift doit etre sur la gachette droite par defaut, le turbo sur Y/triangle"; before v0.1.30 the drift was X and the turbo A or the left bumper); keyboard W accelerates, A / D steer, Shift drifts, E fires the turbo (read by key position; do not mention keyboard layouts), never Control by default (with W held it closes a browser tab). Every key and gamepad button can be rebound in the settings (docs/ui.md#settings).
- **Drift is the heart of the gameplay**, in the spirit of Rocket Racing (Psyonix, in Fortnite): holding drift through a turn builds up a boost released on exit, and fills a turbo meter. First version in v0.1.12 (protocol 6): gamepad X (the right trigger since v0.1.30) or keyboard Shift, held with the stick turned, locks a side, slides without losing speed, charges, and pays out a boost on release; a wall loses the charge. Refined in v0.1.13 at the user's request: less thrown to the outside (the body angle is only drawn, the path follows the drift radius), no speed lost leaving a drift, a boost that is felt. v0.1.14, user's request "like Rocket Racing, a new driving mode where it skates": the drift answers the stick at once (`drift_steering_response`), the path sticks to the heading, the body swings 20 to 45 degrees. v0.1.16, user's feedback "path better, but steer much more gently in a drift, feel it unscrew and glide": drift rotation and body swing build up over 0.6-0.75 s (`drift_steering_response` 4, `drift_angle_response` 3), path still following the heading. v0.1.18, user's request "the longer you hold a drift, the more it should brake you": the drag grows with the charge (`drift_drag_ramp`), so a drift is taken through a turn and let go of. Both to be judged. Rebuilt on 2026-09-20 at the user's request "you go into a drift when you turn off the axis [...] no need to hold the button, but if you do you tighten the turns more [...] when you come back in line with the velocity, you leave the drift, unless you hold it": the slide became real, which ran the car wide of every corner, why `serpentine` was deleted and the roads grew to 28 m. Rebuilt again on 2026-09-27 (v0.1.3, protocol 16) from a recording of Rocket Racing the user supplied (`../rr_drift_example.mp4`, analyzed frame by frame, and measured against the sim): **the path and the body are kept apart.** The stick sets the curve the travel follows; the body (`Car::body`) swings up to `drift_angle` (55°) across it in about a third of a second, drawn and deciding when the drift ends, but never carrying the car wide. A tap of the button with the stick turned starts a drift, the user's way ("j'appuie peu de temps pour passer en drift et je relache. Mais il arrive aussi de devoir la maintenir pour serrer un virage davantage"), and turning hard still does too. Straightening the stick brings the body back into line and ends the drift, which pays a boost of a fifth over top speed (48 m/s), unless the button is held. Held, the button tightens the curve and costs speed, more the longer it is held (the rule of v0.1.18, moved from the drift to the button, since the recording drifts for seconds at top speed); it carries the drift down a straight, and with the stick against the drift carries it over to the other side with its charge. The charge shows as green segments on the road around the back of the car, as in Rocket Racing, and in the HUD gauge, now green too (docs/simulation.md). On 2026-09-28 (v0.1.4, protocol 17), the user found it "beaucoup mieux" and asked for the steering to be smoother ("fais en sorte que ca braque plus fluidement"): the nose jerked, 479°/s on the tick a drift began, turning back on itself when the stick eased, 382°/s the other way when it straightened. The wheel (`Car::steering`) now turns toward the stick at `steering_rate` (center to full lock in 0.2 s, grip and drift alike), the body swings as a critically damped spring (`drift_angle_response` 10, `Car::body_rate`), and its angle eases in from the center instead of following a square root; the nose's rotation never changes by much more than 40°/s from one tick to the next, at the price of a slower swing (45° at about 0.4 s) and a drift ending 0.5 s after the stick straightens. Later the same day (v0.1.5, protocol 18), the user reported "une petite latence avant de braquer qui doit disparaitre. Ca doit devier doucement avant de s'accentuer legerement": the wheel ramped at a fixed rate and the yaw followed it through a lag of its own, two delays in a row (3% of the rotation on the first tick). The wheel now closes a share of its gap every tick (`steering_rate` 14 per second), so it moves most on the very tick the stick does, and the yaw follows it almost at once (`steering_response` and `drift_steering_response` 60, smoothing only changes of radius): half lock turns the car at 14% of its eventual rate on the first tick, 42% at 50 ms, 72% at 100 ms, still without jumps. On 2026-10-03 (v0.1.12, protocol 20), the user found the level excellent and asked to refine the drift: "when you steer, it waits a tiny bit, and then it steers too hard. Rather than resistance, it should unscrew at once, and slowly, before building up gradually". Traced tick by tick with a scratch tool outside the repository, the body's spring pulled hardest at the start, so the body barely moved, then lunged: a tap of 0.1 s at full lock took the nose's rotation to 288°/s at 0.12 s, the tap itself pulling the turn 40% tighter while it lasted, and breaking away by turning hard jumped it by 93°/s in one tick after a quarter of a second of grip. Now the body's swing gathers speed at `drift_swing_acceleration` (450°/s²) up to `drift_swing_rate` (110°/s) and brakes onto its angle (1° at 50 ms, 15° at 0.25 s, 55° at 0.75 s), the drift's curve tightens from the gripping car's to `drift_radius_tight` as the body swings out, and the button's tightening comes in over `drift_button_tighten_time` (0.4 s), so a tap barely tightens: the nose turns at 53°/s after 50 ms, 150°/s after 0.18 s and at most 192°/s, held from 0.25 to 0.5 s, never changing by more than about 18°/s from one tick to the next, tapped into or broken into. The price: an S carried through on the button takes 1.2 s instead of 0.5. The autopilot laps the skyway drifting in 45.9 s, clean. To be judged: the feel above all, `drift_swing_acceleration` (how quickly the unscrewing gathers), `drift_swing_rate` (how hard it turns at most), `steering_rate` (14), `drift_angle` (55), and the boost; all of them hot-reload from `car.ron` while driving. On 2026-11-11 (v0.1.23, protocol 23), the user asked to "Polish the handling. Increase the boost out of a drift. Add sounds. Add a turbo bar". The boost: 52 m/s instead of 48 (three tenths over top speed), 45 m/s² instead of 35, up to 1.2 s instead of 1, charged a quarter faster; 54 was tried and made the autopilot six ticks late scrape. **The turbo meter** (three charges, which the recording fires as a big "BOOSTED" on a button prompt): drifting fills it, a charge for five seconds of drift charge (3.3 s at full lock), and a press spends one on 2 s toward 60 m/s; it is in the car, so it is predicted, and the HUD draws three magenta bars over the speed. The polish, all in `car.ron`: a press of the drift button is remembered 0.15 s, so one made just before the stick turns still starts its drift; a drift survives a graze of a wall (under 3 m/s into it) and charges nothing while it touches; a wall deflects a gripping car along itself in three ticks, the body swinging round after it, where a shallow hit used to grind on with its nose in (35 to 15 m/s in two seconds, now 30); and a car running along a wall without going into it loses nothing. The autopilot fires its turbo where the road runs straight: the skyway in 41.5 s drifting, clean, against 45.9 before, 44.4 without the turbo. To be judged: all of it, above all the size of the boost, how quickly the turbo fills and what a charge is worth. On 2026-11-12 (v0.1.32, no protocol change), the user's word "ça déporte trop et trop vite quand on drift et/ou tourne, regarde ça, affine, alourdis encore si nécessaire": measured first (docs/simulation.md#less-carried-out), the car was carried out by its slide while gripping (`grip` 6, the travel 8.4° off the nose at three quarters lock) and, in a drift, by the body thrown 55° across at up to 110°/s, which the chase camera, looking along the travel, shows as the car swept sideways; the drift's path itself was not wide, and more weight in the rotation changed little and made the late autopilot worse. Now `grip` 9 (5.5°), `drift_entry_angle` 7 (full lock still breaks away, at 0.52 s), `drift_angle` 42, `drift_swing_acceleration` 260 and `drift_swing_rate` 75 (the body 9° out at 0.25 s, 27° at 0.5 s, 41° at 0.75 s, against 15, 43 and 55). Skyway: gripping 51.1 s (52.6), drifting 41.3 s (41.5), both clean, and six ticks late 51.3 s clean and 43.2 s with 3 ticks against a wall (35 before). To be judged: all of it; to try, in `car.ron` while driving, `grip` (9; 7 to 12), `drift_angle` (42; 35 to 50) and `drift_swing_rate` (75; 60 to 100), and `yaw_acceleration` (250) if the car should feel heavier still.
- **Start boost** (v0.1.13, user's request): pressing accelerate right at the start gives a boost graded S to E, timed on the tick the client displayed.
- First milestone: very clean handling on curved roads. The server has full physical authority, loads the test circuit (a small oval) from a file, the client downloads it, and the user can drive it with a gamepad. "Curved turns" means **banked turns**: done in v0.1.10, the road curving up toward the outer wall (parabolic cross-section, 30° at the outer edge on the hippodrome), rising along the clothoid transitions with a smoothstep, gravity pulling toward the inside.
- Look: the track floating with no ground, since v0.1.10 through a city at night of dark towers banded with neon, since v0.1.11 under a starry sky with colored planets, nebulae and turning neon shapes (docs/sky.md), dark road, walls striped dark gray and neon blue, neon blue centerline dashes; since v0.1.13 glowing (HDR bloom, tone mapping still off), hazy, moonlit, the road kerbed and lit by its walls and standing on piers, the city windowed, crowned in a few colors and alive (docs/night.md). Menus: dark translucent panels, neon blue accent, Saira font (OFL, the one file not in the public domain), animated neon grid behind.
- Lobbies (v0.1.11, user's choices): created by players, gone when empty; settings name, track, laps (default 3), players to start (default 2), max players. Waiting (driving freely) → grid 6 s as soon as there are enough players (user's request: 3 s silent, then 4 start lights one a second, the 4th, green with its own burst, lighting at the very start; v0.1.16) → race of N laps (ends when all finished or 30 s after the first) → 8 s results, during which whoever crossed the line is still watching their car drive itself (v0.1.11, the user's report that a solo race gave the wheel straight back) → again. Joining on the grid races; joining after the start spectates until the next one.

## Deployment constraints (certain)

- The server runs on the user's Scaleway machine behind an Apache reverse proxy. Apache terminates TLS (Let's Encrypt) and forwards in plain text to `127.0.0.1:8080`. This rules out QUIC/WebTransport and TLS client certificates.
- **No self-signed certificates.** If native TLS is ever needed, do it properly with a local fake CA.
- The client ships as native desktop **and** wasm. The web build is deployed by `deploy/deploy.ps1` (docs/deploy.md), which also installs the game server, to `https://primo-ideas.xyz/star-racer/` (it was `/space-race/` until the renaming of 2026-11-11, see Status); gamepad play in the browser is expected. Keep every client dependency wasm-compatible.
- Mobile browsers, landscape (v0.1.12, the user's request, their design): the left thumb steers on two buttons, left and right, how hard depending on where it rests (since v0.1.17); the right thumb holds a cross -- touching it anywhere accelerates, and sliding from its hub onto a branch calls that branch's function. Drift is the first branch, straight up, and since v0.1.23 the turbo the second, to the left; the other two are drawn as the empty slots they are, waiting for what follows. The whole interface follows: the menus are laid out for a screen 400 units high instead of 720 (440 before v0.1.17), with everything pressed a thumb high, inside the safe area a notch leaves, the browser drops its details panel and a tap on a row joins, the HUD leaves the thumbs their corners and gains a LEAVE button, and no key hints are shown. The client asks the browser whether the pointer is coarse; `?touch` or `--touch` forces it (docs/ui.md, docs/web.md). **Never tried on a real phone.**

## CI

Five separate GitHub workflows (separate README badges): build server, test server (server + protocol + sim + logger), build client native (Linux), build client wasm, and deploy. The deployment could not exist before September 2026: the old machine had no IPv4 (the user would not pay for one), GitHub-hosted runners have no IPv6 egress, and github.com has no AAAA at all, so neither direction was reachable. The new Scaleway machine has an A record as well as an AAAA one, so `deploy.yml` runs the tests and then cross-compiles, uploads and installs, on a push to main or on demand. It needs the `DEPLOY_SSH_KEY` repository secret and a machine set up by the user's `~/Documents/setup-server.sh`, which is outside both repositories because it sets up the whole host. `deploy/deploy.ps1` stays, for putting a build online without a commit (docs/ci.md, docs/deploy.md).
