# Web build

The client runs in the browser from the same code as the native one, compiled to
`wasm32-unknown-unknown`. It renders with WebGL2 and talks to the same server over WebSocket.

## Tools

```sh
rustup target add wasm32-unknown-unknown
cargo install wasm-server-runner   # runs the web client locally
cargo install wasm-opt             # shrinks the module for deployment
```

Both `wasm-server-runner` and a standalone `wasm-bindgen` CLI must match the `wasm-bindgen`
version in `Cargo.lock` exactly (0.2.129 today). `wasm-server-runner` 1.0.1 accepts any 0.2
release and `cargo install` takes the newest one, so it matches as long as the lock is up to date
with crates.io; a mismatch shows up as an error naming both versions.

## Running locally

Start the server as usual, then, from the repository root:

```sh
cargo run --release -p star-racer-client --target wasm32-unknown-unknown
```

`.cargo/config.toml` sets `wasm-server-runner` as the runner for the wasm target: it generates the
JavaScript bindings, serves the game on <http://127.0.0.1:1334> and stays up until stopped. Settings
go in the page address, for example <http://127.0.0.1:1334/?nickname=Primo>.

This is the one build that uses `-p`: the server cannot compile to wasm, and the wasm target has a
cache of its own, so it does not disturb the native builds. The first one compiles all of Bevy for
the new target (25 minutes on the current development machine); later ones are incremental.

## Building for deployment

The runner serves its own page. A deployable build uses `client/web/index.html` instead, with the
module generated by the `wasm-bindgen` CLI and shrunk by `wasm-opt`:

```sh
cargo build --profile web -p star-racer-client --target wasm32-unknown-unknown
wasm-bindgen --target web --no-typescript --out-dir dist --out-name star-racer-client \
    target/wasm32-unknown-unknown/web/star-racer-client.wasm
wasm-opt -Oz --enable-bulk-memory --enable-sign-ext --enable-nontrapping-float-to-int \
    --enable-mutable-globals --enable-reference-types --enable-multivalue \
    dist/star-racer-client_bg.wasm -o dist/star-racer-client_bg.wasm
cp client/web/* dist/
```

`deploy/deploy.ps1` and the "Deploy" workflow do exactly this. The `web` profile and the flags
`wasm-opt` is given are explained under [Size](#size).

`dist/` must be served over HTTP — browsers refuse to load modules from `file://` — with `.wasm`
files as `application/wasm`.

## Settings

With no command line, the web client reads its settings from the page address:

| Parameter | Native equivalent | Default |
| --- | --- | --- |
| `server=ws://…` | `--server` | the page's own host (see below) |
| `nickname=…` | `--nickname` | none: the login screen |
| `lobby=…` | `--lobby` | none: the lobby list |
| `track=…` | `--track` | the skyway |
| `laps=…`, `min_players=…` | `--laps`, `--min-players` | 3, 2 |
| `create_dialog` | `--create-dialog` | off |
| `settings` | `--settings` | off; opens the settings over the first screen |
| `quick_play` | `--quick-play` | off; with `nickname`, straight into a race |
| `ranked` | `--ranked` | off; with `nickname`, straight into the ranked queue |
| `identity=…` | `--identity` | the browser's main identity |
| `autopilot` | `--autopilot` | off |
| `autopilot_drift` | `--autopilot-drift` | off |
| `touch` | `--touch` | whether the browser says the pointer is coarse |
| `safe_area=T,R,B,L` | `--safe-area` | what the browser says a notch takes (see [Interface](ui.md#on-a-touchscreen)) |
| `latency` | `--latency` | off; F3 shows the figures anyway (see [Latency](latency.md)) |
| `log=error\|warn\|info\|debug\|trace` | `--log` | `warn` (see below) |

For example `?nickname=Primo&identity=second`. The interface has not been tried in a browser yet.
`?touch` shows the phone interface in a desktop browser, which is the quickest way to see it.

Without `server=`, a page served from a site connects to `wss://<the same host>/<its own
directory>/ws`: deployed at `/star-racer/`, the client reaches `/star-racer/ws`, which the reverse
proxy forwards to the game server (see [Deployment](deploy.md)). A page served from `127.0.0.1`,
where no proxy stands in front, falls back to `ws://127.0.0.1:8080/ws` instead.

## On a phone

The web client is the only one a phone can run, so the phone is the browser's business. The
client decides for itself that it is being touched -- `matchMedia("(pointer: coarse)")`, which
`?touch` overrides -- and lays the interface out for a thumb (see
[Interface](ui.md#on-a-touchscreen)). `client/web/index.html` does the rest, most of it in CSS,
so it holds while the module is still loading:

- **The viewport is fixed**: `width=device-width`, no zooming, `viewport-fit=cover` so the canvas
  reaches into the notch. An invisible element padded by `env(safe-area-inset-*)` tells the game
  what the notch, the corners and the home bar take, which the interface keeps clear of (see
  [Interface](ui.md#on-a-touchscreen)).
- **The page is as high as what the browser shows** (`100dvh`, after `100%` for older
  browsers): on a phone, `100%` can be the height with the browser's bars hidden, which would
  put the bottom of the game, and the thumbs' controls with it, under the toolbar.
- **`touch-action: none` on the body**, with `overscroll-behavior: none` and no text selection,
  long-press menu or tap highlight. This is what lets a thumb slide from the hub of the cross onto
  a branch: without it the browser takes that slide for a scroll and the game never sees it.
  Safari ignores `user-scalable=no`, so its `gesture*` events are cancelled as well, and a pinch
  never zooms the page.
- **Sound starts on the first touch.** A browser lets a page play sound only once someone has
  touched it, and Bevy opens its audio context as it starts, before anyone has, so the context
  waits, suspended. Chrome starts it by itself at the first click; Safari never does, and a phone
  stayed silent. The page keeps every audio context the game opens (it wraps the `AudioContext`
  constructor before the module loads), and each touch, click or key resumes any that is not
  running: the first one, and again after a call or another app took the sound away.
- **The screen stays on** while the game is in view on a coarse-pointer screen: between races,
  waiting for players or watching one, nobody touches it, and it went dark. The screen wake lock
  is let go whenever the page is hidden, so it is taken again each time it comes back.
- **Back asks before leaving a lobby.** On a phone, back is a swipe in from the edge, which a
  thumb steering near the left edge makes by accident, and it left the game, race and all. In a
  lobby the game adds a step to the page's history (`history.pushState`, same address); going
  back takes that step instead, and the game asks whether to leave the lobby, as LEAVE does.
  Staying puts the step back; leaving through the button takes it out, so it never costs one
  more press of back for nothing (`ui/back.rs`). In a desktop browser the back button does the
  same.
- **Portrait says to turn the phone.** The game is drawn wide and wants a bottom corner for each
  thumb, so a full-page notice covers portrait on any coarse-pointer screen.
- **A loading screen** stands over the page until the game has drawn a second's worth of frames
  in a row, none held: through the download, the module's compilation, and the browser compiling
  the game's shaders, which on a first visit holds the page still for half a minute or more
  (see [Protocol](protocol.md#handshake)). Its ring turns on the compositor, so it keeps turning
  while the page is held; without it a first visit was a black page, then a frozen one.
- **The home screen.** `manifest.webmanifest` (full screen, landscape, `icon.png` and
  `icon-192.png`) and Apple's `apple-mobile-web-app-*` meta tags: added to a phone's home screen,
  the game opens on its own, full screen and in landscape. It is the only way to full screen on an
  iPhone, whose Safari cannot put a page full screen. The icon is drawn by a script, a neon
  circuit with the player's orange car on the game's dark blue; `deploy.ps1` and the workflow copy
  every file of `client/web/`.

Elsewhere the game offers full screen with a button rather than taking it on the first touch: the
browser's bars take a seventh of the height, but taking the screen over without being asked is
not this game's to do (see [Interface](ui.md#on-a-touchscreen)).

**Typing** goes through the browser's prompt: Bevy's text fields read key events, and a soft
keyboard never opens for a canvas.

**A phone loses its connection all the time** -- moving from Wi-Fi to its mobile network, the
browser put to sleep while the player answers a message -- and the game now connects again on
its own and goes back into the lobby it was in (see
[Architecture](architecture.md#client-networking)).

Checked in headless Edge emulating a phone held in landscape (915 by 356, touch, coarse pointer),
on the local web build, with touches sent through the DevTools protocol: the loading screen, the
nickname typed through the prompt and reaching the lobby list, FULL SCREEN offered on both
screens, a lobby created from the dialog, and a race steered at three quarters, gently and at
full lock with the drift branch held. Then (v0.1.17), the same way, with six lobbies open: the
list dragged with a finger and scrolled without joining anything, a row tapped and its lobby
joined, `history.back()` opening the leaving question and STAY putting the step back, LEAVE
taking it out, the car driven from the cross, the page's WebSockets closed and the game back in
its lobby in 0.6 s, the safe area read through `env()` from insets set by
`Emulation.setSafeAreaInsetsOverride`, and a spectator's two buttons switching the car watched.
Not checked: full screen itself, which a headless browser refuses, the vibration, the wake lock,
sound starting on a phone, and a real phone. Under emulation `devicePixelContentBoxSize` comes back
in CSS pixels rather than device pixels, so the canvas is sized as if the density were 1 while
winit reads the density from `devicePixelRatio`: the interface comes out 2.6 times too large. It
is the emulation, not the game -- a real phone reports device pixels -- so layouts are checked
at a density of 1.

## What differs from native

- **The network session runs on the page's event loop** (`wasm_bindgen_futures::spawn_local`)
  instead of a thread with a tokio runtime: browsers give wasm no threads. The session code is
  the same; only `spawn_session` differs.
- **The identity key lives in local storage**, in hexadecimal, per site. `identity=` selects
  another slot, so two tabs can be two players; the same identity in a second tab takes the first
  one's place, and the first says so.
- **No clean close on exit.** Native blocks the last frame until the Close frame is sent; on the
  web that would block the very event loop that sends it, and closing the page closes the socket.
- **No capture mode**, which writes files.
- **One shadow cascade**: WebGL2 supports no more.

Two build settings are easy to miss and do not show up as compilation errors:

- Bevy's **`web` feature** (enabled for wasm in `client/Cargo.toml`). Without it Bevy's clock is
  `std`'s, which compiles and then panics in the browser the first time it reads the time.
- `getrandom`'s **`wasm_js` feature** (in `protocol/Cargo.toml`), so key generation and nonces use
  the Web Crypto API.

## Size

The module is downloaded whole before the first frame, so its size is the wait of a first visit.
Built in release with Bevy's default features it weighed 117.8 MB, 52.4 MB after `wasm-opt -Os`,
and 14.5 MB on the wire once Apache had compressed it. Since v0.1.26 it weighs **23.9 MB after
`wasm-opt`, and 7.5 MB compressed** (`gzip -9`), half of what it was. Two things did it.

**Only the Bevy the game uses.** `client/Cargo.toml` turns Bevy's default features off and names
the ones the game calls, grouped by what they are for. The defaults bring glTF, scenes,
animation, sprites, gizmos, anti-aliasing, the tone mapping tables, compressed textures and an
Ogg decoder; the game builds its meshes and synthesizes its sounds in code, and keeps tone
mapping off, so it calls none of them, and the linker cannot always tell: a plugin that is
registered is code that is reached. The native build takes the same list plus `png`, for
`--capture`. A feature the game starts to need has to be added there; forgetting one is a
compilation error or, for a plugin, something that silently does not happen, which is why the
build was checked by a race captured natively and another in a browser.

**A profile of its own**, `[profile.web]` in the workspace `Cargo.toml`, inheriting from release:

| Setting | Why |
| --- | --- |
| `opt-level = "s"` | Size first. Not `"z"`, which also stops unrolling and vectorizing the loops the renderer runs every frame. |
| `lto = "fat"`, `codegen-units = 1` | The whole program optimized as one unit: what is never called goes, what is the same is merged. |
| `panic = "abort"` | No unwinding tables or landing pads. A browser tab can do nothing with a panic but stop. |
| `strip = true` | No symbol names in the module. |

It is slow to build, 32 minutes from nothing on the development machine (measured while a debug
build of the workspace ran beside it), which is the reason it is a profile of its own: nothing
else pays for it, and release stays what it was.

`wasm-opt -Oz` then takes the module `wasm-bindgen` wrote from 29.1 MB to 23.9 MB, in a little
over a minute. Stripping removes the section in which the compiler names the WebAssembly
features the module uses, and without it `wasm-opt` refuses the module's own instructions, so
the features Rust turns on for this target are named on its command line.

Measured on 2026-11-11 (Rust 1.99.1, `wasm-opt` 0.116.1): 32.1 MB out of the compiler, 29.1 MB
after `wasm-bindgen`, 23.9 MB after `wasm-opt`.

## Verified

In headless Chrome with software rendering (SwiftShader, no GPU), against a local server, three
ways: the `wasm-bindgen` build served over HTTP, the same build after `wasm-opt -Os`, and
`cargo run` through `wasm-server-runner`. Each time the module loads, renders the track, connects,
authenticates with a key from local storage, joins under the nickname from the address and
downloads the track; with `autopilot` it drives. The server logs the player joining, the car moving,
and leaving when the browser closes.

Software rendering ran at 2 to 3 frames per second, too slow for the autopilot to steer cleanly: it
works from a view that far behind the car and zigzags (see
[Simulation](simulation.md#autopilot)). That says nothing about a real GPU.

On the deployed site (2026-11-06), in headless Edge on the GTX 1050 Ti through ANGLE and
Direct3D 11, driven over the DevTools protocol: a first visit, with an empty profile, opens the
socket 4.9 s in and then holds the page's thread until 34 s compiling shaders, which is what
lengthened the server's handshake deadline to 2 minutes (see [Protocol](protocol.md#handshake));
a second visit connects in 50 ms, enters the lobby and builds the track at 5 s, then freezes 10 s
compiling the race's shaders before the race runs.

The `web` profile build of v0.1.26 (2026-11-11), with Bevy cut down to the features the game
uses, served locally against a local server in headless Edge on the GTX 1050 Ti: straight into
a race from the address, the drifting autopilot half a minute into its lap at 61 fps, the sky,
the bloom, the HUD with its turbo meter and the latency figures all drawn, input to screen at
33 ms and 0.0 cm corrected, nothing at error level in the console.

## A console with nothing in it

The game says nothing while it runs well. `LogPlugin` is set to `warn`, so a browser console
opened on a healthy game is empty, and anything appearing in it is worth reading. `?log=info`
brings back what the game has to say about itself, and `debug` or `trace` more still.

The rendering crates are pinned at `error` whatever the level: on WebGL2, Bevy warns four times
at startup that it cannot load order-independent transparency, background motion vectors, screen
space ambient occlusion and the atmosphere. All four are about what the machine can do, the game
uses none of them, and the only thing a player could do with those lines is take them for a fault.

Measured rather than reasoned about: headless Chrome loading the deployed page, entering a lobby
and driving a lap shows three console lines, all three the audio notice below.

## Known gaps

- **Size**: 23.9 MB, 7.5 MB compressed (see [Size](#size)). What is left is mostly the renderer
  and its shaders; `opt-level = "z"` and a look at what the module holds, function by function,
  have not been tried.
- `wasm-opt` 0.116 bundles Binaryen 116. It reads the modules Rust 1.98 produces today; a newer
  Rust enabling newer WebAssembly features by default could need a newer Binaryen.
- Tried with a GPU only in a headless browser, and not yet with a gamepad or on a phone. The touch interface has
  been looked at in a phone-shaped window on a desktop (`--touch --window-size 844x390`) and its
  gestures are covered by tests, but no finger has ever been put on it.
- In one of the first three headless runs the connection dropped after about 40 seconds (the server
  saw a reset); every other run held until the browser closed. Not understood yet; to watch on a
  real GPU.
- **The one line left in the console.** Chrome logs `The AudioContext was not allowed to start`,
  three times, as the page loads. It is its autoplay policy: a page may not open an audio context
  before someone has clicked in it, and Bevy opens one as it starts. The page resumes it at the
  first touch, click or key (see [On a phone](#on-a-phone)) and the sound then works, so the line
  is a notice and not a fault. Removing
  it would mean not building `AudioPlugin` until a gesture, which Bevy cannot do after startup --
  the game would have to ship without sound in the browser. Left as it is, deliberately.
