# Web build

The client runs in the browser from the same code as the native one, compiled to
`wasm32-unknown-unknown`. It renders with WebGL2 and talks to the same server over WebSocket.

## Tools

```sh
rustup target add wasm32-unknown-unknown
cargo install wasm-server-runner   # runs the web client locally
cargo install wasm-opt             # shrinks the module for deployment
```

Both `wasm-server-runner` and a standalone `wasm-bindgen` CLI must match the `wasm-bindgen`
version in `Cargo.lock` exactly (0.2.128 today). `wasm-server-runner` 1.0.1 accepts any 0.2
release and `cargo install` takes the newest one, so it matches as long as the lock is up to date
with crates.io; a mismatch shows up as an error naming both versions.

## Running locally

Start the server as usual, then, from the repository root:

```sh
cargo run --release -p space-race-client --target wasm32-unknown-unknown
```

`.cargo/config.toml` sets `wasm-server-runner` as the runner for the wasm target: it generates the
JavaScript bindings, serves the game on <http://127.0.0.1:1334> and stays up until stopped. Settings
go in the page address, for example <http://127.0.0.1:1334/?nickname=Primo>.

This is the one build that uses `-p`: the server cannot compile to wasm, and the wasm target has a
cache of its own, so it does not disturb the native builds. The first one compiles all of Bevy for
the new target (25 minutes on the current development machine); later ones are incremental.

## Building for deployment

The runner serves its own page. A deployable build uses `client/web/index.html` instead, with the
module generated by the `wasm-bindgen` CLI and shrunk by `wasm-opt`:

```sh
cargo build --release -p space-race-client --target wasm32-unknown-unknown
wasm-bindgen --target web --no-typescript --out-dir dist --out-name space-race-client \
    target/wasm32-unknown-unknown/release/space-race-client.wasm
wasm-opt -Os dist/space-race-client_bg.wasm -o dist/space-race-client_bg.wasm
cp client/web/index.html dist/
```

`dist/` must be served over HTTP — browsers refuse to load modules from `file://` — with `.wasm`
files as `application/wasm`.

## Settings

With no command line, the web client reads its settings from the page address:

| Parameter | Native equivalent | Default |
| --- | --- | --- |
| `server=ws://…` | `--server` | the page's own host (see below) |
| `nickname=…` | `--nickname` | none: the login screen |
| `lobby=…` | `--lobby` | none: the lobby list |
| `track=…` | `--track` | the esplanade |
| `laps=…`, `min_players=…` | `--laps`, `--min-players` | 3, 2 |
| `create_dialog` | `--create-dialog` | off |
| `identity=…` | `--identity` | the browser's main identity |
| `autopilot` | `--autopilot` | off |
| `autopilot_drift` | `--autopilot-drift` | off |
| `touch` | `--touch` | whether the browser says the pointer is coarse |
| `latency` | `--latency` | off; F3 shows the figures anyway (see [Latency](latency.md)) |
| `log=error\|warn\|info\|debug\|trace` | `--log` | `warn` (see below) |

For example `?nickname=Primo&identity=second`. The interface has not been tried in a browser yet.
`?touch` shows the phone interface in a desktop browser, which is the quickest way to see it.

Without `server=`, a page served from a site connects to `wss://<the same host>/<its own
directory>/ws`: deployed at `/space-race/`, the client reaches `/space-race/ws`, which the reverse
proxy forwards to the game server (see [Deployment](deploy.md)). A page served from `127.0.0.1`,
where no proxy stands in front, falls back to `ws://127.0.0.1:8080/ws` instead.

## On a phone

The web client is the only one a phone can run, so the phone is the browser's business. The
client decides for itself that it is being touched -- `matchMedia("(pointer: coarse)")`, which
`?touch` overrides -- and lays the interface out for a thumb (see
[Interface](ui.md#on-a-touchscreen)). `client/web/index.html` does the rest, and all of it in
CSS, so it holds while the module is still loading:

- **The viewport is fixed**: `width=device-width`, no zooming, `viewport-fit=cover` so the canvas
  reaches into the notch.
- **`touch-action: none` on the body**, with `overscroll-behavior: none` and no text selection or
  tap highlight. This is what lets a thumb slide from the hub of the cross onto a branch: without
  it the browser takes that slide for a scroll and the game never sees it.
- **Portrait says to turn the phone.** The game is drawn wide and wants a bottom corner for each
  thumb, so a full-page notice covers portrait on any coarse-pointer screen.

Nothing asks for fullscreen. A browser's own bars leave about 330 logical pixels of height in
landscape, which the interface still fits, and taking the screen over without being asked is not
this game's to do.

What a phone still cannot do: **type**. Bevy's text fields read key events, and a soft keyboard
never opens for a canvas, so the nickname and the lobby name are whatever they are offered --
the dice rolls another nickname, and the lobby is named after its creator. **Switching the
watched car while spectating** has no touch control either, and a long lobby list cannot be
scrolled by dragging it.

## What differs from native

- **The network session runs on the page's event loop** (`wasm_bindgen_futures::spawn_local`)
  instead of a thread with a tokio runtime: browsers give wasm no threads. The session code is
  the same; only `spawn_session` differs.
- **The identity key lives in local storage**, in hexadecimal, per site. `identity=` selects
  another slot, so two tabs can be two players; the same identity twice is rejected by the server.
- **No clean close on exit.** Native blocks the last frame until the Close frame is sent; on the
  web that would block the very event loop that sends it, and closing the page closes the socket.
- **No capture mode**, which writes files.
- **One shadow cascade**: WebGL2 supports no more.

Two build settings are easy to miss and do not show up as compilation errors:

- Bevy's **`web` feature** (enabled for wasm in `client/Cargo.toml`). Without it Bevy's clock is
  `std`'s, which compiles and then panics in the browser the first time it reads the time.
- `getrandom`'s **`wasm_js` feature** (in `protocol/Cargo.toml`), so key generation and nonces use
  the Web Crypto API.

## Verified

In headless Chrome with software rendering (SwiftShader, no GPU), against a local server, three
ways: the `wasm-bindgen` build served over HTTP, the same build after `wasm-opt -Os`, and
`cargo run` through `wasm-server-runner`. Each time the module loads, renders the track, connects,
authenticates with a key from local storage, joins under the nickname from the address and
downloads the track; with `autopilot` it drives. The server logs the player joining, the car moving,
and leaving when the browser closes.

Software rendering ran at 2 to 3 frames per second, too slow for the autopilot to steer cleanly: it
works from a view that far behind the car and zigzags (see
[Simulation](simulation.md#autopilot)). That says nothing about a real GPU.

## A console with nothing in it

The game says nothing while it runs well. `LogPlugin` is set to `warn`, so a browser console
opened on a healthy game is empty, and anything appearing in it is worth reading. `?log=info`
brings back what the game has to say about itself, and `debug` or `trace` more still.

The rendering crates are pinned at `error` whatever the level: on WebGL2, Bevy warns four times
at startup that it cannot load order-independent transparency, background motion vectors, screen
space ambient occlusion and the atmosphere. All four are about what the machine can do, the game
uses none of them, and the only thing a player could do with those lines is take them for a fault.

Measured rather than reasoned about: headless Chrome loading the deployed page, entering a lobby
and driving a lap shows three console lines, all three the audio notice below.

## Known gaps

- **Size**: the release module weighs 112.9 MB. `wasm-opt -Os` brings it to 51.8 MB (six minutes on
  the current development machine) and the result still runs, but that is still far too much to
  download. The build itself needs a size-oriented profile too: link-time optimization,
  `opt-level = "z"` or `"s"`, stripped symbols.
- `wasm-opt` 0.116 bundles Binaryen 116. It reads the modules Rust 1.98 produces today; a newer
  Rust enabling newer WebAssembly features by default could need a newer Binaryen.
- Not yet tried in a browser with a GPU, with a gamepad, or on a phone. The touch interface has
  been looked at in a phone-shaped window on a desktop (`--touch --window-size 844x390`) and its
  gestures are covered by tests, but no finger has ever been put on it.
- In one of the first three headless runs the connection dropped after about 40 seconds (the server
  saw a reset); every other run held until the browser closed. Not understood yet; to watch on a
  real GPU.
- **The one line left in the console.** Chrome logs `The AudioContext was not allowed to start`,
  three times, as the page loads. It is its autoplay policy: a page may not open an audio context
  before someone has clicked in it, and Bevy opens one as it starts. The context resumes by itself
  at the first click and the sound then works, so the line is a notice and not a fault. Removing
  it would mean not building `AudioPlugin` until a gesture, which Bevy cannot do after startup --
  the game would have to ship without sound in the browser. Left as it is, deliberately.
